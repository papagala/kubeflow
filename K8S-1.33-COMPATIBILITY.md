# Kubeflow on Kubernetes 1.33 — Compatibility Findings

Author: Oswaldo Gomez
Date: 2026-07-06
Scope: Does each Kubeflow release install and function on Kubernetes v1.33?

This is a working record for the platform team's k8s 1.33 migration. It is not an
official Kubeflow statement. Read the Limitations section before quoting any result.

## TL;DR

| Kubeflow | k8s 1.33 verdict | Basis |
|----------|------------------|-------|
| 1.10.2 | Works, with two image fixes | Full install, cluster healthy, V1+V2 pipelines run, notebooks + KServe pass. No fully-green CI run yet (blocked by test-runner limits, not k8s). |
| 1.11.0 | Works | Full install, cluster healthy, V1+V2 pipelines run, notebooks + KServe + Spark pass. No fully-green CI run yet (blocked by test-runner disk, not k8s). |
| 2026.03.1 | Does not work | Knative Serving control plane crashloops on 1.33. Confirmed k8s-specific (see control run). |
| master (dev) | Does not work | Same Knative Serving failure as 2026.03.1. |

One-line takeaway: 1.10.x and 1.11.x are fine on Kubernetes 1.33. 2026.03 and the
current dev line are not — their Knative Serving requires a newer Kubernetes (they
ship pinned to 1.36).

## What "compatibility" actually rests on

There is no separate, sophisticated per-version Kubernetes conformance suite behind
Kubeflow's supported-version claims. Support is validated by a single end-to-end CI
job, `.github/workflows/full_kubeflow_integration_test.yaml`, which stands up the full
stack on a 3-node KinD cluster and runs pipeline/notebook/KServe/Katib/etc. tests.
This report reproduces that same job, per version, with the cluster pinned to k8s
v1.33.1. If you want a different answer, that is the job to change.

## Method

Work was done on a public fork: https://github.com/papagala/kubeflow

For each version, a branch was cut from the release tag and three mechanical changes
were made so the upstream job can run on a personal fork:

1. Remove the job guard `if: github.repository == '<upstream>'` (it skips the job on
   any non-upstream repo). Note the guard string changed across releases because the
   upstream repo was renamed from `kubeflow/manifests` to `kubeflow/community-distribution`.
2. Replace the self-hosted runner label (`ubuntu-latest-16-cores` on 1.10.x,
   `oracle-vm-16cpu-64gb-x86-64` on newer) with the free `ubuntu-latest`.
3. Pin the KinD node image to k8s v1.33.1 (see per-version notes; releases default to
   different Kubernetes versions).

The k8s v1.33.1 node image used throughout:
`kindest/node:v1.33.1@sha256:050072256b9a903bd914c0b2866828150cb229cea0efe5892e2b644d5dd3b34f`
with `kind v0.29.0` (the release that publishes that image).

## Results

### Kubeflow 1.10.2 — works on 1.33, needs two image fixes

Branch: https://github.com/papagala/kubeflow/tree/v1.10.2-k8s1.33

The v1.10.2 tag already targets k8s 1.33 by default, so no Kubernetes override was
needed. Two of its pinned container images have since been removed from public
registries (unrelated to Kubernetes) and had to be repointed before the stack would
install:

| Broken image | Status | Replacement |
|--------------|--------|-------------|
| `docker.io/bitnami/kubectl:1.30.4` | 404 (Bitnami removed public Docker Hub images, Aug 2025) | `docker.io/bitnamilegacy/kubectl:1.30.4` |
| `gcr.io/ml-pipeline/minio:RELEASE.2019-08-14T20-37-41Z-license-compliance` | 404 | `docker.io/minio/minio:RELEASE.2019-08-14T20-37-41Z` (same MinIO release 1.11.0 uses) |

Files changed:
- `common/oauth2-proxy/components/cluster-jwks-proxy/kustomization.yaml`
- `applications/pipeline/upstream/third-party/minio/base/minio-deployment.yaml`

With those fixes, on k8s 1.33 the run installs the full stack, all pods reach Ready,
and it passes Dex login, pipeline integration, V1 and V2 pipeline execution, SeaweedFS
isolation, and the volumes API.
Evidence (full install + pipelines green, k8s 1.33):
https://github.com/papagala/kubeflow/actions/runs/28792259190

Not yet fully green. Two late-stage, non-k8s failures were seen across runs:
- First run failed in the in-notebook pipeline step: the script polls the KFP `healthz`
  endpoint from inside the notebook and got HTTP 503 five times, then timed out. The
  pipelines themselves had already passed via port-forward, so this was a transient
  in-mesh 503, not a broken pipeline.
- After fixing the notebook race (below), a later run hung in the Spark test and was
  killed by the 60-minute job timeout on the free runner.
  Run: https://github.com/papagala/kubeflow/actions/runs/28804664038

### Kubeflow 1.11.0 — works on 1.33

Branch: https://github.com/papagala/kubeflow/tree/v1.11.0-k8s1.33

Defaults to k8s 1.34.0; overridden to 1.33.1 for this test. No image fixes needed — it
already uses `docker.io/bitnamisecure/kubectl:latest`, which is anonymously pullable.

On k8s 1.33 it installs everything (Knative, KServe, Pipelines/SeaweedFS, all apps),
all pods reach Ready, and it passes Training Operator, Trainer, Dex login, V1 and V2
pipeline execution, SeaweedFS isolation, volumes API, KServe, and Spark.
Evidence (full install + pipelines green, k8s 1.33):
https://github.com/papagala/kubeflow/actions/runs/28792260729

Not yet fully green. After the notebook-race fix, the run reached the Ray test and
failed pulling the Ray image with `no space left on device` — the runner's ~14 GB disk
was exhausted by the cumulative image set. This is a runner limit, not k8s 1.33.
Run: https://github.com/papagala/kubeflow/actions/runs/28804665928

### Kubeflow 2026.03.1 and master — do NOT work on 1.33

Branches:
- https://github.com/papagala/kubeflow/tree/26.03.1-k8s1.33
- https://github.com/papagala/kubeflow/tree/master-k8s1.33

Both default to k8s 1.36.1; overridden to 1.33.1. Both fail at the same step, `Install
Knative Serving`. The Knative control-plane pods (activator, autoscaler, controller,
webhook, net-istio-controller/webhook) crashloop, failing their liveness/readiness
probes with HTTP 500; istiod also reports 503. The install never completes.

Runs:
- 2026.03.1: https://github.com/papagala/kubeflow/actions/runs/28792262128
- master: https://github.com/papagala/kubeflow/actions/runs/28792263688

This is a genuine Kubernetes-version incompatibility, not a runner problem. Proof: the
same master branch, on its native k8s 1.36, on the same free `ubuntu-latest` runner,
passed the entire 38-minute suite green.
Control run (master on k8s 1.36, fully green):
https://github.com/papagala/kubeflow/tree/master-native136 —
https://github.com/papagala/kubeflow/actions/runs/28793542120

The exact minimum Kubernetes version for 2026.03/master was not bisected. It is
somewhere in 1.34–1.36; only 1.33 (fail) and 1.36 (pass) were tested.

## Quirks and gotchas worth carrying into the migration

1. Image rot is the main hazard for old releases, not Kubernetes. Pinned images
   disappear from public registries over time (the Bitnami Docker Hub purge; a removed
   gcr.io MinIO tag). An old manifest that "no longer installs" is usually a dead image
   reference, fixable by repointing, not a k8s problem. Check image availability first.

2. Knative Serving is the version gate for k8s. The newer Knative shipped in 2026.03
   and dev does not run on k8s 1.33. If the migration target is 1.33, 2026.03/dev are
   off the table until Knative is downgraded or k8s is newer.

3. Flaky notebook readiness check (affects the test harness, any k8s). The step runs
   `kubectl wait --for=condition=Ready pod -l app=test` immediately after applying the
   Notebook CR. If the notebook-controller has not created the pod yet, `kubectl wait`
   returns `error: no matching resources found` and exits non-zero without waiting. Fix
   is to poll for the pod to exist first, then wait for Ready. This is a test bug, not a
   product or k8s issue, but it will make CI look red intermittently.

4. Free GitHub runners are too small for the full suite. `ubuntu-latest` (~14 GB free
   disk, 60-minute default job cap here) cannot hold the complete image set; the tail of
   the suite (Ray's multi-GB image) hits `no space left on device`, and long runs hit
   the timeout. Upstream uses 16 vCPU / 64 GB self-hosted runners for a reason. Use a
   comparable runner, or relocate the Docker data-root to the runner's larger `/mnt`
   volume, to get fully-green runs.

5. Running the job on a fork needs two edits. Remove the `github.repository` job guard
   and swap the self-hosted runner label for one you actually have. The guard string
   differs by release (`kubeflow/manifests` vs `kubeflow/community-distribution`).

6. Kubernetes pinning differs by release. 1.10.x and 1.11.x hardcode the `kindest/node`
   image inline (three node entries) in
   `tests/install_KinD_create_KinD_cluster_install_kustomize.sh`. 2026.03/master use
   `KIND_VERSION` and `KIND_NODE_IMAGE` variables at the top of the same script.

## Limitations

- Each cell is a small number of runs (often one), not a statistical sample. Treat
  green/red as directional.
- 1.10.2 and 1.11.0 have not produced a single fully-green run here. Everything that
  exercises the Kubernetes API surface passed; the outstanding failures are runner disk
  and job-timeout limits on free `ubuntu-latest`. A confirming green run on a
  16 vCPU / 64 GB runner (or with Docker on `/mnt`) is the outstanding to-do.
- Only k8s 1.33.1 was tested for the "works" verdicts, and 1.36.1 for the control. No
  bisection of the 2026.03/master minimum k8s version.
- Results are from a fork with mechanical CI edits (guard, runner, k8s pin) plus the
  image fixes noted for 1.10.2. No Kubeflow application code was changed.

## Reproduce

```
# Pick a version branch on the fork
gh workflow run full_kubeflow_integration_test.yaml \
  --repo papagala/kubeflow --ref <branch>   # e.g. v1.11.0-k8s1.33

# To test a different Kubernetes version, change the kindest/node image
# (and KIND_VERSION on 2026.03/master) in
# tests/install_KinD_create_KinD_cluster_install_kustomize.sh
```
